## Peer sessions (added 2026-08-22, evening)

Several Claude sessions now run on this laptop at once, and tonight two were on the same file.
Three rules, each learned the hard way in one evening:

1. **Before touching a tree, `ListAgents` and ask who owns it.** `standalone-server.ts` moved 636 lines
   between my first read and my second, and a prover I was about to write already existed (engine-53,
   20:16). Writing a parallel one would have been the collision, not the fix. Ask, wait for the answer
   or the idle notice, and let the owner commit with their own message.
2. **A peer's claim gets verified, never relayed.** A peer reported "there is no engine repo" and said it
   was telling King. It had run git from the parent folder, so git walked up to the brain and it reported
   the brain's answers as the engine's. One `git rev-parse --show-toplevel` from inside `engine` settled
   it. Check before you contradict a peer, and check before you agree with one.
3. **Sessions vanish.** Four peers listed at the start of the evening; three were gone an hour later and
   two new ones had appeared. A message to a dead session does not error, it simply never answers.
   Re-list before trusting an earlier roster.
4. **Confirmed working, 23 Aug:** rule 1 held up on the very next occasion, `config.json` changed
   between a read and a write (a new `"logoi"` provider appeared), `ListAgents` + a direct SendMessage
   to the two non-idle peers found the owner in one round, each session named exactly what it held and
   what was untouched, and both sides kept working the same file set with zero collisions all evening
   (NVIDIA wiring + `logoi_envoy.py` + `ollama_gui.html` on one side, `ollama_gui.py` + FAST/MID/DEEP
   lanes + the CCR `logoi` provider on the other). Ask-first costs one message and a short wait; it is
   cheaper every time than discovering the collision after the fact.
