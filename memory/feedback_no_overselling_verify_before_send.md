King, 2026-06-20: *"you said it would [be] like the tiktok video, it is not, it is exactly like before… you can't just be sending me errors. I would prefer if you send me something and it was correct and I didn't like it. How can we prevent this going forward?"*

**The rule:** correctness + an honest, plain description beat hype. To King, a deliverable that doesn't match how I described it IS an error, as bad as a broken one.

**Why:** he's phone-first, time-poor, and has been burned by several rounds of "this will be like X" that then weren't. Trust erodes every time I oversell.

**How to apply (do every time, no reminder):**
1. **No overselling.** Never say a deliverable is "like [King's reference]" / "wow" / "interactive 3D" unless I've literally matched it (ideally side-by-side). Describe what it **is** AND what it **is NOT**, in plain words, when I send it.
2. **Verify as the user before sending.** Actually use it the way King will, walk it, tap every control, on a phone-sized screen, and confirm it does what I claimed. If it doesn't match his reference, tell him the gap honestly *instead of* sending. (Extends [[feedback-qa-before-handover]] from "does it work" to "does it match what I said + the reference".)
3. **Confirm the METHOD achieves the goal BEFORE building** (e.g., ask which explore mode), so I don't ship the wrong format and burn a round.
4. **State hard limits up front** (e.g., a single photo has no data to "walk into"), not after he's disappointed.
5. Pairs with [[feedback-always-send-gmail-and-link]] (deliver to his phone) and [[feedback-qa-until-king-approves]] (loop till he's happy).
