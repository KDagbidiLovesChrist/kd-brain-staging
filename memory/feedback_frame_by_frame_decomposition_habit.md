# Frame by frame decomposition habit

**The rule:** When a dense brief, spec, or contract comes in, turn it into a numbered frame register via `commands\frame-by-frame-decompose.md` instead of reading it raw. Each frame gets three layers:
1. **Process** (0 to 9 to 0, not-started to executing, honest zeros at the start)
2. **Foundation** (binary: does the output exist)
3. **Quality** (a real ladder if the source supports 5 levels, or honest binary if it does not; each stage checked three independent ways: textual trace, rubric map, plausibility; disagreement or ambiguity marked as `x`, unresolved variable, never forced)

**Why:** Proven once in full (2026-08-26/27) against a real 30-frame college design brief. Cross-validated by `/find-skills` against GitHub's Spec Kit (calls this "unit tests for English") and ThinkUpfront/Upfront (calls ambiguity "unknown" state, independent confirmation the method's shape is right). Method extracts a skill, `commands\frame-by-frame-decompose.md`, now T2 in `_ops\SKILL_TIER_LEDGER.md`.

**How to apply:** Next time a spec/brief/contract lands dense and long, reach for the frame-by-frame method instead of summarizing on the fly. Finds the source's own defects (missing steps, restarted numbering, a term used twice) and flags them rather than silently fixing them, which makes the register more accurate not less, it stays faithful to what was actually asked. Build the TODO from the frames, not written twice. Unresolved items stay marked `x`, not guessed at: that's where King's own answer or clarification lives, waiting for him, not for Claude to fill in the blank.
